# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

tktk (placeholder name — editorial shorthand for "to come") is a prototype feedback interface for a mini-LMS aimed at poetry, essay, and short story writing workshops. It is being built to gather feedback from a poetry instructor at Brooklyn Poets and is not production software — favor fast iteration over hardening, and there is no backend or test suite by design.

Possible future scope beyond the feedback interface: manuscript editing and review.

## Stack and constraints

- React + TypeScript, built with Vite. Any reasonable frontend framework was acceptable but React was the strong preference.
- Visualizations (when added) must use D3.js (`d3` + `@types/d3` are already installed).
- Routing via `react-router-dom`.
- No backend — app state (workshop, students, poems, comments) is seeded into `localStorage` on first load (`src/lib/storage.ts`) and read/written from there. There is no server-side persistence, and none is expected at this stage. The storage key is versioned (`tktk:vN`); bump it whenever `seedData.ts`'s shape or content changes materially, so stale cached data in someone's browser doesn't shadow the new seed.
- Must render usably on phone, tablet, and desktop browsers — this is how feedback gets gathered from the stakeholder, so check responsive behavior at mobile widths, not just desktop.
- Visual design: black and white, serif typefaces throughout (see `--serif` in `src/index.css`). Keep new UI consistent with this rather than introducing color or sans-serif type.
- No e2e/automated test suite — this is an intentional prototype-stage decision, not an oversight.

## Architecture

Single-page app, client-only, seeded fake data standing in for a future backend.

- `src/types.ts` — core domain types: `Student`, `Poem` (includes `classNumber`, the workshop session it was submitted for, and `body`, the full poem text), `Workshop` (includes `totalClasses`, used to render tabs even for classes with no submissions yet), `Comment` (a highlight + note tied to a poem via character offsets), `Reply` (a flat, single-level reply on either a `Comment` or an `OverlayStroke`'s note — `parentId` just references whichever unique id, there's no separate "kind" field since both id spaces are already distinct strings), `Author` (not persisted — `{name, initials}` resolved at render time from an `authorId`, see `getAuthor` in `PoemFeedback.tsx`). `authorId` — on `Comment`, `Reply`, *and* `OverlayStroke` — is either a `Student.id` or the current user's username ("scha") — there's no separate Author collection to keep in sync.
- `src/data/seedData.ts` — the actual demo content (workshop name/instructor, the five student "poets," their poems, and — for Dickinson's poem specifically — a simulated peer-feedback thread: one comment from each of the four classmates plus the instructor, two reply exchanges between classmates, and all four classmates' freehand markup marks with their own notes — added to show what a real workshop discussion on this page looks like across both feedback systems). Dickinson's poem body is the real, public-domain text; the other four poems' bodies are lorem ipsum placeholders (they're still under copyright, or — for Crane — text this codebase's author couldn't reproduce word-for-word with confidence). Swap in real, rights-cleared text there when available; nothing else needs to change. The seed comments use a `findRange(body, excerpt)` helper that `indexOf`s the quoted excerpt rather than hardcoding character offsets — do the same for any new seed comments, since hand-computed offsets drift silently the moment the poem text changes and `indexOf` catches the mismatch (throws) instead. Seed *markup* strokes have no such luxury — there's no text-offset equivalent for freehand `{x,y}` coordinates — so their positions were estimated against the rendered layout and then corrected against real screenshots until they visibly lined up under the intended line (for an underline, nudge `y` down slightly from a line's exact vertical center or the mark reads as a strikethrough instead). Two of the four (Lorde, Crane) are a circle→line→circle gesture — one continuous stroke that circles one word, draws a line across to a second word elsewhere in the poem, and circles that too — with the one `comment` attached to the whole stroke, since there's no mechanism for one note to span multiple separate strokes. Ellipse points for a circle are easiest generated programmatically (`cx/cy/rx/ry` → points around the loop) rather than placed by hand; see git history for the small throwaway script used here if you need to add more.
- `src/lib/storage.ts` — the only data-access layer. `getState()` lazily seeds `localStorage` from `seedData.ts` on first call and returns the current app state (workshop, students, poems, comments, overlayStrokes, replies, current user). `addComment`/`deleteComment`/`getCommentsForPoem`, and their `addReply`/`deleteReply`/`getRepliesForPoem` and `saveStroke`/`getStrokesForPoem` counterparts, read-modify-write the relevant arrays. Follow this pattern (read full state, mutate, save whole state back) for any new mutations rather than introducing a different persistence approach. Deleting a comment/note cascades to its replies (`deleteComment`, `clearStrokeComment`, `clearStrokesForPoem` all also filter `state.replies`) — any new "delete the parent" path needs the same cascade or it'll orphan replies that no longer render anywhere. `clearStrokesForPoem(poemId, authorId)` takes an explicit author now — it used to wipe every stroke for a poem regardless of who drew it, which would have let "Clear marks" delete a classmate's marks along with your own once strokes could belong to different authors.
- `src/App.tsx` — route table. `/` is the workshop home page; `/poems/:poemId` is the feedback page.
- `src/pages/WorkshopHome.tsx` — renders tabs for every class 1..`workshop.totalClasses` (not just ones with poems — classes with no submitted poems render as a dashed "pending" tab), styled like notebook divider tabs (`.tabs`/`.tab`/`.tab--active`/`.tab--pending` in `index.css`), with the poem list for the selected class in a bordered "notebook page" panel. Poems within a class are split into "awaiting feedback" and "feedback given" sections by `poem.status`.
- `src/pages/PoemFeedback.tsx` — the annotation UI: poem text on the left, a comments sidebar on the right (stacks below on narrow viewports). The page has two mutually-exclusive top-level modes, `feedbackMode: "highlight" | "markup"` (a segmented `.mode-switch` control, defaults to `"highlight"`) — mouse text-selection-and-comments, or stylus/touch freehand drawing. They're never both visible or interactive at once; see the `useMarkupOverlay` entry below for how switching to markup mode blocks text selection "for free," without any extra guard code. The Comments sidebar itself stays visible in both modes (only the inline highlight marks and markup ink toggle); this was a deliberate choice when asked, not an oversight — don't hide it in markup mode without checking first.
  - **Highlight mode.** Selecting text in `.poem-body` computes plain-text character offsets (`getOffsetWithin`, using the `Range.setEnd` + `range.toString().length` trick) relative to `poem.body`, not DOM positions — this is what lets highlights survive being re-rendered as `<mark>` spans. Selection is captured on `mouseup`/`touchend` on the poem-body container specifically (not a document-wide `selectionchange` listener) — that was tried first and broke two ways: `selectionchange` fires continuously mid-drag, locking in whatever was selected first instead of the full drag, and it also fires when the comment textarea takes focus, which collapses `window.getSelection()` and wiped out the pending comment. Scoping to `mouseup`/`touchend` on the container sidesteps both, since clicking into the sidebar textarea never fires it. The pending (unsaved) selection is rendered as its own `<mark className="highlight highlight--pending">` in `renderedBody` — not left to the browser's native selection highlight — so it visibly stays blue while the user is writing the comment, even after focus moves to the textarea. Highlights are light-blue `<mark className="highlight">` spans; being outside `feedbackMode === "highlight"` just adds a `.highlights-off` class that strips their background via CSS, it doesn't affect the underlying comment data. Comments render sorted by `start` offset and collapse individually (`CommentCard`). Hovering a comment card pulses its highlight twice (`pulsingHighlightId` state, `.highlight--pulsing`); clicking a highlight scrolls to and pulses its comment card twice (`pulsingCommentId` state, `.comment-card--pulsing`). Both are fixed two-cycle CSS animations (`animation: ... 2`) triggered once on `mouseenter`/`click` and cleared via a matching `setTimeout`, not tied to hover duration — they play out fully even if the mouse leaves immediately. Kept as two separate state variables rather than one shared "active id" since the two directions (card→highlight, highlight→card) are independent.
  - **Markup mode.** See `useMarkupOverlay` below.
- `src/components/` — shared presentational pieces (`PoemListItem`, `AuthorModal`, `Avatar`, `CommentCard`, `MarkupCommentCard`, `ReplyThread`). The author modal (bio, workshop history, avatar) is opened from the poem list; keep it reusable rather than inlining it into a single page if it needs to appear elsewhere later. `ReplyThread` (flat reply list + toggleable reply composer) is shared by both `CommentCard` and `MarkupCommentCard` — it owns its own "is the reply box open" state locally, unlike the page-level composers, since a reply box only ever concerns the one already-expanded card it's inside and needs no poem-wide coordination. `CommentCard` and `MarkupCommentCard` share the same `.comment-card` markup/CSS almost entirely, but their header avatar and excerpt are deliberately styled differently (`.comment-card-avatar--markup` red border vs. the default black; `.comment-card-excerpt--markup` unquoted/non-italic vs. the quoted italic poem excerpt) — that's the only thing letting you tell a markup-mark comment apart from a text-highlight comment in the sidebar list at a glance. Giving both card types an identical avatar treatment once already quietly erased this distinction; don't let a future "let's make these more consistent" pass do it again without keeping *some* visible marker between the two.
- `src/hooks/useMarkupOverlay.ts` — freehand stylus/touch/mouse markup over the poem (for iPad-style circle-and-annotate use), largely separate from the text-selection comment system above and not yet unified with it (that's future work, per the person who asked for this) — but each mark can now carry its own optional note (`OverlayStroke.comment?: string`), which is the one place the two systems already resemble each other. Takes `(poemId, enabled, viewAuthorId)`.
  - **`viewAuthorId`** is who the page's "View: [author]" dropdown is currently set to — defaults to the current user ("my marks"), and can be switched to any classmate to look at *their* marks. The hook's `strokes` return value is **every** author's strokes for the poem, unfiltered — the page relies on that: it filters `strokes` down to `viewAuthorId` itself for what actually gets drawn on the poem (`visibleStrokes` in `PoemFeedback.tsx`), but deliberately does *not* filter the sidebar's markup-comments list the same way, so you can read every classmate's notes regardless of whose ink is currently on screen ("show all the markup comments" was an explicit call, not an oversight — don't scope that list by `viewAuthorId`). Interaction stays correctly scoped without a separate filtered-strokes concept, though: `eraseAt` and the comment tool's hit-test only ever consider strokes where `stroke.authorId === viewAuthorId`, and new strokes are saved with `authorId: viewAuthorId` — so you can never erase, comment on, or accidentally extend a mark that isn't the one you're currently looking at, even though the full (unfiltered) set is sitting right there in `strokes`.
  - **`enabled`** is owned by the page — it's `feedbackMode === "markup" && viewAuthorId === currentUser.username`. Viewing a classmate's marks is read-only: `enabled=false` disables the whole pointer-handling pipeline (and the page separately grays out the Draw/Erase/Comment buttons via `disabled`), so there's no path to drawing "as" someone else. Going disabled also resets any in-progress stroke and closes any open note popover.
  - Within markup mode there's always exactly one active `tool`, `"draw" | "erase" | "comment"` (no fourth "off" state — the page only mounts the Draw/Erase/Comment segmented switch at all when markup mode is active).
  - Strokes (`OverlayStroke`, in `types.ts`) are stored as arrays of `{x, y}` **fractions** (0..1) of the poem-body box, not pixels — that's what lets a mark drawn on an iPad render in the same relative spot on a phone or desktop later. Rendering exploits this directly: the `<svg>` overlay uses `viewBox="0 0 1 1"` with `preserveAspectRatio="none"`, so stroke points can be used as path coordinates with no pixel math, and `vector-effect="non-scaling-stroke"` keeps the pen width a constant screen size regardless of container size.
  - Drawing/erasing uses the Pointer Events API (`onPointerDown/Move/Up`) so mouse, touch, and pen all go through one code path — verified against genuine touch input (CDP `Input.dispatchTouchEvent`, not a JS-level `new TouchEvent()`, which does *not* trigger real pointer-event synthesis in Chromium and would give a false negative). **If you're driving this with a headless browser for testing:** re-query the poem-body-wrapper's `getBoundingClientRect()` immediately before each pointer action rather than reusing one captured earlier — a stale rect (e.g. after the page scrolls between actions) silently sends erase/comment hit-tests to the wrong coordinates, which reads exactly like a real scoping bug (it isn't) and burned real time to track down here.
  - The overlay `<svg>` sits absolutely-positioned over `.poem-body` inside `.poem-body-wrapper`, toggled only by a `.overlay-canvas--hidden { display: none }` class when `feedbackMode !== "markup"` — that single class is what makes Highlight/Markup mutually exclusive: hidden, it can't capture pointer events at all so highlight-mode text selection works normally; shown, it fully covers the poem body so stray drags can't reach the text-selection listener underneath. No `pointer-events` juggling needed on top of that.
  - The eraser (`eraseAt`) does real partial erasing — it splits a stroke into surviving runs around whatever points fall within its radius, not delete-the-whole-stroke (note: if an erase cut splits a *commented* stroke, both resulting pieces currently keep a copy of the same comment — acceptable for now, not specifically handled).
  - The comment tool is tap-only (no drag tracking): `handlePointerDown` hit-tests the tapped point against `viewAuthorId`'s stroke points (`findNearestStrokeId`, radius `COMMENT_HIT_RADIUS`, deliberately more forgiving than the eraser's radius since precise tapping is harder than sweeping) and opens `activeCommentStrokeId` for whichever stroke is closest, pre-filling `commentDraft` from its existing comment if any. That composer renders in the sidebar (`.comments-panel`, same spot as the highlight composer — an inline popover positioned at the mark was tried first and rejected for flowing off-screen near the poem's edges), and saved marks with a comment are listed as cards in the same `<ul className="comment-list">` as text comments, via `MarkupCommentCard` (shows the mark's author with the same small initials avatar `CommentCard` uses, now that strokes carry `authorId` too). `removeStrokeComment(strokeId)` is the general-purpose "clear this stroke's comment" used by the sidebar list's delete button — it works on any stroke regardless of author or whether its composer is currently open (an instructor can remove any note); `deleteStrokeComment()` (no args) is the composer's own delete button and just delegates to it with `activeCommentStrokeId`.
  - The small dot markers on commented strokes *in the poem itself* (`.overlay-comment-dot`) are a separate, purely visual indicator, drawn only for `visibleStrokes` — `pointer-events: none`, real tap hit-testing happens on the SVG regardless of where on the stroke you tap, not specifically on the dot. Tapping a `MarkupCommentCard` in the sidebar (`handleToggleMarkupComment` in `PoemFeedback.tsx`) scrolls to and pulses that dot twice (`pulsingDotId` state, `.overlay-comment-dot--pulsing`, a fixed two-cycle CSS animation cleared via `setTimeout`) — the same card→highlight pulse pattern used for text comments, via a `dotRefs` ref map parallel to `highlightRefs`/`commentCardRefs`. Note this only visibly does anything if the commented stroke belongs to `viewAuthorId` — otherwise its dot isn't rendered at all right now, so the pulse is a harmless no-op.
  - One gotcha already hit here: never put a side effect (`saveStroke`, `replaceStrokesForPoem`, anything touching `localStorage`) inside a `setState` updater function — React StrictMode double-invokes updaters in dev specifically to catch that, and it was silently duplicating every saved stroke. Read the value from state/closure and call the side effect outside the updater instead.
- The "logged in" user is hardcoded in the seed data as instructor Sam Cha (`scha`) — there is no real auth, and the feedback page has no concept yet of what a student/poet would see (it's instructor-only right now). `Comment`/`Reply` do carry an `authorId` (see above) so seeded/simulated feedback can be attributed to different classmates, but every comment or reply created *live* through the app while there's only one real user is still always attributed to `currentUser.username` — there's no UI for picking "who's commenting," since that's still just you.

When adding pages/features, follow the existing pattern: seed content in `seedData.ts`, types in `types.ts`, data access through `storage.ts`, route-level component in `pages/`, shared UI in `components/`.
